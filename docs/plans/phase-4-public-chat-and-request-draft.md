# Plan: Phase 4 Public Chat and Request Draft

## Goal

Deliver a deterministic, customer-facing BuildPro web workflow that operates without OpenAI. A visitor can start an isolated conversation, choose a supported action, provide one field at a time, edit collected values, review a server-generated summary, explicitly confirm it, and receive the backend-generated reference for exactly one request. The request, customer, conversation, initial status history, routing, and any eligible pre-existing attachment metadata are linked atomically and the request becomes visible through the existing authorized employee dashboard.

Phase 4 is complete only when the normal quotation and site-visit request path works end to end with no model call, duplicate messages and confirmations are safe, public callers have no direct table access, and tenant/customer data cannot be obtained with a guessed UUID or request reference.

## User value

Customers can submit a complete request even when no AI provider is configured or available. BuildPro receives consistent, confirmed information instead of an incomplete free-form lead, and employees see the result in the request queue without re-entering it.

## Documentation reconciliation

The source documents agree that request creation occurs only after a complete server-stored draft is explicitly confirmed and that duplicate confirmation returns one request/reference. The following differences materially shape the design but do not block planning:

1. `docs/05_DATABASE_SCHEMA.md` describes nullable `conversations.customer_id`, intent, collected fields, and confirmed fields; the actual table requires a customer and lacks the draft columns. Use a dedicated one-to-one `conversation_drafts` table and make `customer_id` nullable. This keeps workflow state structured and avoids frequently rewriting the conversation record.
2. The API contract says a “signed public conversation token,” while the request asks for an opaque token. Use a cryptographically random opaque bearer secret stored only as a hash. Authenticity comes from unguessability and hash comparison; it is not a self-contained signed token and exposes no claims.
3. The roadmap defers general rate limiting to Phase 9, but this task explicitly requires it for public endpoints. Phase 4 includes a minimal database-backed public rate limiter only; repository-wide/edge/provider hardening remains Phase 9.
4. Attachments are an MVP requirement but upload is scheduled for Phase 6. Phase 4 confirmation will safely relink already validated message attachments if any exist and will be tested with database fixtures, but it will not expose upload/presign endpoints or storage UI.
5. Full natural-language intent classification belongs to Phase 5. Phase 4 accepts explicit menu/action identifiers and deterministic field answers. Unrecognized free text receives a safe menu/clarification response rather than inferred intent.
6. Full human-handoff workflow is Phase 7 and request-status verification is Phase 8. Their initial menu choices return accurate unavailable/escalation guidance; they do not create fake handoffs or disclose status.

- BuildPro Cameroon remains active with the six seeded services and three seeded departments.
- Service-to-department configuration is the primary deterministic routing source. Quotation/site-visit requests fall back to the active Commercial Department only when the selected service has no department; ambiguous or missing routing fails safely rather than choosing by name silently.
- English is the delivered locale. The API accepts only supported locale values and keeps canonical identifiers separate from display strings so French can be added later.
- The public chat is same-origin with Next.js. The token is therefore kept in an HttpOnly, `Secure` in production, `SameSite=Lax` cookie rather than browser storage or JavaScript-readable JSON.
- One browser may have one active Phase 4 conversation cookie at a time. Supporting parallel customer conversations requires a later cookie/session design.
- Phone validation normalizes Cameroon input to a documented canonical value before persistence. A dedicated phone library is added only if repository-owned parsing cannot meet the tested Cameroon cases.
- Customer reuse by phone must be conservative. Match an existing customer only within the same organization and normalized phone; otherwise create a customer. Never merge across tenants, and do not overwrite an existing non-null email/name silently.
- The minimum database-backed limiter is appropriate for pilot traffic. A distributed edge/provider limiter is deferred until Phase 9.

## Deterministic customer workflow

### State model

Use a pure state machine owned by `lib/domain/conversation-workflow.ts`. Suggested stages:

```text
choose_action
  -> choose_service
  -> collect_name
  -> collect_phone
  -> collect_email
  -> collect_location
  -> collect_description
  -> collect_preferred_start
  -> collect_budget
  -> review
  -> confirmed

any editable stage -> edit_menu -> edit_field -> review
any unconfirmed stage -> cancelled
```

The next stage is computed from the selected request type, active service configuration, and server-stored draft. The browser never supplies the current stage as authority. Required fields are asked before optional fields. Each successful answer stores one field and returns exactly one next question or the summary.

### Initial customer options

The opening response identifies itself as BuildPro Cameroon’s virtual assistant and offers stable action codes with display labels:

1. `request_quotation`
2. `request_site_visit`
3. `ask_about_services`
4. `check_request_status`
5. `report_problem`
6. `speak_to_employee`

Quotation and site visit enter guided collection. Service information displays only active seeded service catalogue data and lets the customer select a service. Problem/support enters a support request draft with Customer Support routing and the same minimum identity/description confirmation rules. Status and employee options explain the safe next step without exposing status or fabricating a handoff; their complete workflows remain later phases.

### Draft fields

Store typed fields in `conversation_drafts`, not in client state or message parsing:

- `intent`: closed action enum.
- `request_type`: `quotation`, `site_visit`, or `support` in Phase 4.
- `service_id`: same-organization active service.
- `customer_name`.
- `phone_normalized` and `phone_confirmed_at`.
- `email` nullable.
- `preferred_contact_method` nullable.
- `description`.
- `location`.
- `preferred_start_date` nullable.
- `budget_min`, `budget_max`, and `budget_currency` nullable as one bounded optional group.
- `structured_details jsonb` for validated service-specific fields only; default `{}`.
- `stage`, `version`, `cancelled_at`, `summary_version`, `confirmed_at`, and timestamps.

Required for quotation/site visit: customer name, confirmed phone, active service, description, location, request type, and explicit confirmation. Support/problem requests require name, confirmed phone, description, and confirmation; service may be a configured support service or nullable only if the existing request constraint is deliberately retained as nullable. Email, preferred contact method, preferred start date, budget, structured service fields, and attachments are optional.

The implementation must reconcile `services.required_fields` from the documented schema with the actual table, which currently lacks that column. Phase 4 may add a constrained `required_fields jsonb` configuration, seed empty arrays initially, and support a small allowlisted field-definition format; it must not build a generic no-code form engine.

### Editing and summary

- `review` returns a server-built allowlisted summary plus actions `confirm`, `edit`, and `cancel`.
- `edit` returns editable field codes. Choosing one moves to an edit stage and the next message replaces only that validated field.
- Changing service invalidates service-specific fields and recomputes routing/questions.
- Changing phone clears its confirmation timestamp and asks the customer to confirm the normalized number again.
- Every edit increments draft `version`, invalidates any previous confirmation nonce, and produces a fresh summary.
- The summary contains no internal IDs, token values, routing rules, audit metadata, or employee information.

## Public conversation token design

Generate 32 random bytes with Node cryptography when the conversation is created. Return it only through a host-only HttpOnly cookie with `SameSite=Lax`, `Secure` outside local development, a bounded expiry, and no broad domain attribute. Store a versioned SHA-256 digest and token expiry in a new `public_conversation_access` row; never store or log the raw token.

Each conversation endpoint:

1. Parses and validates the UUID path.
2. Reads the cookie and hashes the presented token.
3. Uses constant-time comparison after selecting by conversation ID and active token version.
4. Checks expiry, revocation, active organization, conversation state, and organization linkage.
5. Derives organization scope from the access row/conversation, never request JSON.

Rotate the token after successful request confirmation and revoke it when the conversation is closed or explicitly cancelled. Confirmation may continue returning the request reference in that response, but later status lookup requires Phase 8 verification. Missing, expired, revoked, wrong-conversation, and cross-tenant tokens return the same customer-safe not-found/session-expired shape.

## Confirmation nonce and idempotency

When a complete draft enters `review`, generate a separate high-entropy nonce. Store only its digest, bound to `conversation_id`, `draft.version`, `summary_version`, purpose `confirm_request`, and a short expiry. Return the raw nonce in the customer-safe summary response. A field edit, cancellation, expiry, or successful confirmation invalidates it.

Confirmation accepts only:

- `confirmation: true`
- `confirmationNonce`
- `idempotencyKey` as a UUID

It never accepts draft/customer/request fields. The repository invokes a single transaction-safe database function that locks the conversation, draft, and nonce; verifies token-derived conversation scope, nonce digest/version/expiry, complete required data, active service and department, and confirmation state; then creates or returns the request using `(organization_id, idempotency_key)`.

Retry behavior:

- Same conversation and idempotency key: return the existing request and reference.
- Same conversation after successful confirmation with a different key: return the already-linked request, never create another.
- Same idempotency key belonging to another conversation: return conflict without revealing its request.
- Concurrent confirmation calls: one transaction creates the request; all successful retries return that request.
- A failed transaction consumes nothing and leaves the draft reviewable unless the nonce itself is invalid/expired.

## Request-creation transaction

Add a narrowly scoped `security definer` function such as `public.confirm_public_request(...)`, but revoke it from `public`, `anon`, and `authenticated`; call it only through the server-side repository. Give it a fixed empty `search_path`, explicit qualification, bounded inputs, and a reviewed owner. The function must not accept organization, customer fields, service, department, request status, or reference from the browser.

In one transaction it:

1. Locks and validates the token-authorized conversation, draft, and nonce.
2. Checks the organization and selected service are active.
3. Revalidates required fields and phone confirmation.
4. Resolves or inserts the same-tenant customer conservatively.
5. Resolves deterministic routing from the active service department, request type, and configured fallback.
6. Inserts the request with status `new`, server-owned title/description/location/structured details, `confirmed_at`, and the supplied idempotency key.
7. Lets the existing trigger allocate the reference and create initial status history; set transaction-local source to `public_conversation` so history provenance is correct.
8. Updates both reciprocal request/conversation links and sets `conversations.customer_id`.
9. Creates a department-only assignment history row for the initial route when a department exists, with a system/public source represented without pretending an employee performed it.
10. Relinks only validated, same-organization attachment metadata already associated with customer messages in this conversation; no storage operation occurs in Phase 4.
11. Marks the draft and nonce consumed/confirmed.
12. Writes append-only `request.created` and initial-routing audit events with no phone, email, message body, token, or nonce.
13. Returns only request UUID, reference, canonical status, and creation timestamp.

The existing request trigger remains the only reference allocator. No TypeScript or SQL path may supply a reference or use `MAX + 1`.

## Message persistence and duplicate handling

Add `client_message_id uuid` for customer messages and `reply_to_message_id uuid` for assistant messages, with tenant-safe composite foreign keys and partial unique indexes:

- One customer message per `(organization_id, conversation_id, client_message_id)`.
- At most one deterministic assistant reply per customer message.

`POST /messages` validates a bounded `clientMessageId`, action/answer payload, and optional optimistic draft version. A controlled repository transaction locks the conversation/draft, returns the existing exchange for a duplicate ID, otherwise stores the customer message, applies exactly one deterministic state transition, stores the assistant response, and returns both. Concurrent duplicates must produce one customer message, one state update, and one assistant reply.

Do not infer state from message text or rebuild critical fields from history. Messages are the customer-visible transcript; `conversation_drafts` is the authoritative structured state.

## API design

### `POST /api/conversations`

Input: `organizationSlug`, supported locale, and an optional browser-generated creation idempotency key. Resolve only an active organization by slug, apply creation limits, create the conversation/access/draft/initial assistant message atomically, set the token cookie, and return `201`. A duplicate creation key within the same rate-limit/browser scope returns the same conversation without exposing its token in JSON.

### `GET /api/conversations/[conversationId]`

Requires the opaque cookie. Return an allowlisted transcript containing customer/assistant/employee messages only, current safe state, current prompt/actions, draft progress, and summary when applicable. Exclude system/tool messages, metadata, internal notes, audit rows, storage paths, other requests, token digests, rate-limit keys, and nonce digests.

### `POST /api/conversations/[conversationId]/messages`

Requires the opaque cookie. Accept a structured union such as `{clientMessageId, kind: "action", action}` or `{clientMessageId, kind: "answer", value}`. Persist and deduplicate the exchange, update one draft field/stage, and return a deterministic assistant message and actions. Unsupported natural language returns a menu or current-question clarification without changing unrelated fields.

### `PATCH /api/conversations/[conversationId]/draft`

Requires the opaque cookie. Accept `{field, value, expectedVersion}` for explicit edits only. The service owns the editable-field allowlist and field-specific schema. Return the updated draft/summary or a typed stale-version conflict.

### `POST /api/conversations/[conversationId]/summary`

Requires the opaque cookie. Revalidate completeness, issue/replace the confirmation nonce, persist the server summary version, and return summary plus nonce. Incomplete drafts return `draft_incomplete` with the next single question, not a nonce.

### `POST /api/conversations/[conversationId]/confirm-request`

Requires the opaque cookie and bounded JSON. Accept only confirmation, nonce, and idempotency key. Return `201` for the first creation and `200` for an idempotent replay, both with the same reference. Use typed `confirmation_required`, `draft_incomplete`, `nonce_expired`, `conflict`, and sanitized internal errors.

All responses use private/no-store headers and trace IDs. Public endpoints do not accept raw organization IDs, customer IDs, service tenant IDs, request status, reference number, department ID, actor ID, or role.

## Service and repository boundaries

Create a separate public conversation module rather than extending the employee `RequestService` with unauthenticated concepts:

- Domain layer: stages, action codes, field definitions, normalization, completeness, next-question selection, summary mapper, and deterministic routing intent.
- Schema layer: public creation, message union, edit, summary, and confirmation inputs.
- DTO layer: independent public allowlists.
- `PublicConversationService`: workflow and customer-safe typed results. It receives trusted request context containing IP/browser rate-limit hashes, not raw client-selected tenant scope.
- `PublicConversationRepository`: active slug resolution, token verification, conversation/draft reads, atomic message exchanges, summary nonce persistence, and confirmation transaction.
- Supabase adapter: a server-only service-role client for these exact public operations. Every query/function input still carries server-resolved organization scope despite the service role bypassing RLS.
- Route layer: bounded parsing, cookie management, rate-limit context, status mapping, and no business rules.

The employee request repository remains employee-only. Confirmation creates normal request rows, after which the existing dashboard repository/RLS reads them without a special public path.

## Rate limiting and abuse controls

Add a minimal tenant-aware database limiter suitable for a single Supabase-backed pilot. Never store raw IP addresses. The Next.js server derives versioned HMAC digests of IP and a separate browser cookie identifier using a required server-only secret. Do not trust `X-Forwarded-For` unless deployment configuration identifies a trusted proxy; document the production platform header used.

Separate limits by action, for example:

- Conversation creation per IP/browser/organization.
- Message attempts per conversation token and per IP.
- Summary/nonce issuance per conversation.
- Confirmation attempts per conversation and IP.
- Invalid-token attempts per IP.

The database operation atomically increments fixed-window counters and returns remaining/reset information. Enforce request-body limits, message/field lengths, maximum transcript size returned, conversation expiry, maximum draft edits/messages, and no unbounded metadata. Return `429 rate_limited` with `Retry-After` but no indication whether a target conversation exists.

Rate-limit rows contain keyed digests, bucket/action, count, and expiry; they include organization ID when resolved and are never exposed through public RLS. Cleanup can be a documented scheduled maintenance command; an external distributed limiter remains Phase 9.

## Database changes

Create one additive forward migration after the Phase 3 migration. It should:

- Make `conversations.customer_id` nullable and retain its same-tenant composite foreign key.
- Add safe conversation intent/current-stage or keep all stage data in the one-to-one draft table; avoid duplicate sources of truth.
- Create `conversation_drafts` with `organization_id`, `conversation_id`, typed fields, version/check constraints, nonce digest/expiry/consumed fields or a separate one-purpose nonce table, and timestamps.
- Create `public_conversation_access` with organization/conversation composite key, token digest/version, expiry/revocation, creation idempotency digest, and no raw token.
- Add message `client_message_id` and `reply_to_message_id`, composite foreign keys, sender-dependent checks, and partial unique indexes.
- Add `services.required_fields` only with a constrained JSON shape and production-safe default if service-specific fields are implemented now.
- Add an index for active-token lookup by conversation, draft lookup, message replay, expired-token cleanup, rate-limit buckets, and same-tenant normalized customer phone lookup.
- Add `public_rate_limits` or an equivalent private-schema table with atomic increment function and expiry index.
- Extend assignment provenance only if needed to represent system/public initial routing accurately; never insert a fake employee actor.
- Add controlled functions for conversation creation/message application/confirmation only where atomic multi-row behavior warrants them.
- Ensure request insert history uses `changed_by_type='customer'` or a documented system type with source `public_conversation`; do not falsely label it employee/database activity.
- Revoke all new table/function privileges from `public` and `anon`. New public APIs run through the server. Authenticated employee reads are granted only where existing dashboard needs them and remain protected by RLS.
- Enable and force RLS on every new public-schema tenant table, with no broad public policies.
- Regenerate `lib/supabase/database.types.ts` from the resulting local schema.

Do not edit applied Phase 1–3 migrations. Hosted correction is always a new migration.

## Attachment linking boundary

Phase 4 exposes no upload endpoint. The confirmation transaction nevertheless defines and tests the eventual link behavior:

- Only attachment rows already associated with customer messages in the same authorized conversation and organization are eligible.
- The attachment must have passed the status/validation fields introduced by Phase 6 before it may move.
- Relinking changes `message_id` to null and `request_id` to the new request in the same transaction so the existing exactly-one-owner check remains true.
- Storage bucket/path are never returned to the public client.
- Foreign-conversation, foreign-tenant, employee, unvalidated, missing, or already-request-linked attachments are ignored/rejected without partial request creation.

Until Phase 6 adds validated attachment lifecycle fields, the eligible set is empty in production and Phase 4 request creation proceeds without attachments.

## Customer-safe UI

Add a public route such as `/chat/buildpro-cameroon` or `/chat/[organizationSlug]` and components that render:

- Organization identity and an explicit “virtual assistant” disclosure.
- Initial action buttons plus a progressively enhanced text/form input.
- One active question with label, help text, validation feedback, and keyboard focus management.
- A transcript with pending, retryable, duplicate-safe, and persisted indicators.
- Progress showing completed required fields without exposing internal stage names.
- Service selection from active tenant services only.
- Review summary, edit-field menu, explicit confirm checkbox/button, and cancel action.
- Confirmation success with the returned reference and a warning that the reference alone cannot reveal status.

## AI-independent fallback behavior

The deterministic workflow is the primary Phase 4 behavior, not a mock AI implementation:

- Menu selections map to closed action codes.
- The server asks the next question from pure rules and trusted configuration.
- Free text answers only the currently active field.
- Unrecognized action-stage text repeats the supported options and never guesses a service, promise, price, date, or capability.
- Service questions show approved active service catalogue text only; absent information produces “I don’t have confirmed information” plus safe contact/human guidance.
- No environment variable, package, route, or test requires OpenAI.
- Phase 5 will call the same draft/message/confirmation services rather than create a second request path.

## Error handling

Extend typed errors with `rate_limited`, `conversation_expired`, `draft_incomplete`, `stale_draft`, `confirmation_required`, `nonce_expired`, and `duplicate` where needed. Map:

- `400` invalid body/field/action.
- `404` inactive organization or inaccessible conversation, without existence leakage.
- `409` stale draft, invalid workflow action, already-cancelled state, nonce mismatch, or confirmation conflict.
- `410` expired/revoked conversation when revealing that state is safe; otherwise use the uniform inaccessible response.
- `413` oversized body.
- `429` rate limit with bounded `Retry-After`.
- `500` sanitized unexpected failure.

Never expose SQL errors, stack traces, token/nonce values in errors, internal UUID relationships, rate-limit keys, another tenant’s catalogue, or whether a guessed conversation UUID exists.

## Cross-tenant and public-negative scenarios

At minimum, create active organizations A and B with equivalent services and conversations. Prove:

1. An A token cannot read, message, edit, summarize, cancel, or confirm B’s conversation, even with B’s UUID.
2. A token cannot select B’s service or route to B’s department.
3. A nonce from A cannot confirm B or another A conversation.
4. A message ID replayed across conversations does not return the original exchange.
5. A confirmation idempotency key reused across conversations cannot reveal or return another request.
6. A guessed conversation UUID without the opaque token reveals no transcript, draft, customer, request, or existence signal.
7. Anonymous Supabase clients cannot bypass server endpoints to list services, customers, conversations, messages, drafts, requests, attachments, or histories.
8. Failed cross-tenant attempts create no message, draft update, customer, request, reference allocation, attachment link, history, assignment, or audit row.
9. Service-role repository queries always include the server-resolved organization ID and fail tests if that scope is omitted.
10. Public responses never contain internal notes or employee-only fields even after the request appears in the dashboard.

## Security review

- Public callers receive no Supabase table permissions. All operations pass through server routes and typed services.
- The service-role key exists only in a `server-only` module, never uses a `NEXT_PUBLIC_` name, and never enters props, JSON, logs, test snapshots, or browser bundles.
- Service-role repository operations retain explicit organization filters because RLS is bypassed.
- Tenant comes from an active slug at creation and from token-bound database state thereafter, never a message/edit/confirmation body.
- Conversation UUIDs, references, message IDs, and nonce values are not authentication. Only the high-entropy conversation token authorizes draft/transcript access.
- Raw tokens, nonce secrets, IP addresses, and browser limiter identifiers are never stored or logged; only versioned hashes/HMACs are stored.
- Confirmation is bound to a specific complete draft version and is single-use/idempotent.
- Request creation/routing/history/audit/linking occur atomically in PostgreSQL and cannot be reproduced through anonymous table writes.
- Public DTOs are allowlists independent of employee DTOs. They never strip fields from an employee response.
- Input schemas bound body, message, field, transcript, locale, IDs, dates, budget, and action values. Unknown fields are rejected.
- Rate limiting covers creation, messaging, nonce issuance, confirmation, and invalid-token abuse without becoming an existence oracle.
- Errors are sanitized and uniform across missing/foreign/inaccessible conversations.
- Initial service catalogue text is active, tenant-scoped configuration; unsupported questions produce no invented claims, prices, schedules, or guarantees.
- Attachments remain private and unusable in Phase 4 unless already validated by the future Phase 6 lifecycle.
- References are returned only after confirmation and are explicitly not sufficient for status access.
- Audit metadata excludes customer contact data, conversation bodies, tokens, nonce values, and rate-limit keys.

## Known risks and limitations

- A database-backed fixed-window limiter is sufficient for the pilot but less capable than an edge/distributed abuse platform. Trusted-proxy configuration must be correct in production.
- One fixed HttpOnly cookie limits a browser to one active conversation at a time unless cookie naming/session indexing is expanded.
- Phone normalization and conservative same-tenant customer matching need a clearly tested Cameroon policy; shared family/business phone numbers can still represent distinct people and may require later merge/review tooling.
- Abandoned-draft retention duration is not specified. Phase 4 should make expiry configurable and document cleanup, but production retention policy needs business/privacy approval before real customer use.
- Full service-specific field configuration is intentionally narrow. A generic dynamic-form builder remains out of scope.
- Attachment upload/linking cannot be exercised through the Phase 4 UI until Phase 6; only database fixture-level link safety is testable now.
- “Speak to an employee” cannot create a real queued handoff until Phase 7 and must be presented as guidance, not completion.
- “Check request status” cannot reveal status until Phase 8 verification exists.
- The deterministic service-information path is limited to active seeded catalogue descriptions; open-ended grounded FAQ answers arrive with Phase 5 knowledge orchestration.
- Customer reply delivery for an employee’s Phase 3 request-more-information message remains incomplete until Phase 7.
- Hosted migration, secrets, trusted proxy configuration, cleanup scheduling, and post-deployment tenant-negative smoke tests remain operational deployment steps.
